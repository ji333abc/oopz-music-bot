# 专辑点歌模式规划书

> 状态：QQ + OOPZ 文字频道 + Panel MVP 已实现，默认关闭、待灰度验证
> 面向版本：下一功能迭代（建议拆成 4 个可独立回滚的交付批次）
> 产品定义：按专辑检索、确认曲目范围，并将歌曲按唱片曲序批量提交到现有播放队列
> 核心原则：不改变全局播放模式、先确认后入队、批量写入原子化、播放地址按需解析、失败可见且可恢复

## 1. 结论摘要

专辑点歌解决的是“想连续听一张唱片，却必须逐首搜索和点歌”的问题。用户发送
`专辑 <专辑名/歌手>`，从最多 5 个候选中选择一个专辑，查看曲目后再选择整张、前若干首或指定范围加入队列。
空闲时从所选范围的第一首开始播放，忙碌时整批追加到待播队列末尾。

本能力是新的**点歌入口和批量队列来源**，不是 `顺序/单曲循环/随机` 之外的新全局播放模式：

- 顺序模式下，专辑歌曲按“碟号、曲号、上游稳定顺序”依次播放；
- 随机模式下仍服从现有随机规则，提交结果必须提示“随机模式不保证专辑曲序”；
- 不自动清空、插队或覆盖现有队列，也不在专辑结束后恢复某个隐式模式；
- 单首删除、批量删除、拖拽排序继续有效，用户可以在入队后编辑专辑中的个别歌曲。

首版只支持 QQ 音乐，QQ 群与 Panel 共用同一应用服务和响应契约。已确认当前固定版本
`@sansenjian/qq-music-api@2.4.0` 可通过 `/getSmartbox` 检索专辑，并通过 `/getAlbumInfo`
按 `albummid` 返回专辑元数据和曲目；实现不使用“逐首关键词搜索”拼接专辑。

## 2. 背景与当前基线

当前项目已经具备可复用的基础：

- `搜歌 -> 5 分钟候选会话 -> 选歌` 的 requester 隔离交互；
- `排行榜 -> 榜单详情 -> 单首/前 10 首批量加入` 的多步流程；
- `QueueService`、`queue_version`、Redis Lua 和内存降级队列；
- QQ Markdown/Keyboard 回复、Panel 命令入口与 SSE 状态同步；
- QQMusic 搜索缓存、外部请求指标、播放失败历史和 Cookie 状态；
- 当前队列歌曲已有 `song_id/name/artists/album/cover/duration/platform` 等展示字段。

但直接复制“榜单批量”实现并不合适：排行榜最多处理 10 首，并会在提交阶段逐首获取播放地址；专辑可能有
数十首歌曲，整批提前获取临时播放地址会放大延迟、上游压力和链接过期概率。此外，现有
`QueueService.enqueue()` 是单条写入，循环调用会暴露部分成功状态并多次推进 `queue_version`。

因此专辑能力同时需要三个基础改进：专辑领域契约、原子批量入队、队列歌曲的播放地址按需解析。

## 3. 目标与非目标

### 3.1 目标

- 用户能用专辑名、歌手名或二者组合找到正确版本的专辑；
- 在产生播放副作用前展示专辑、歌手、发行日期、曲目数和曲目列表；
- 支持整张、前 N 首和闭区间曲目入队，保持原始唱片顺序；
- 一次命令要么完整写入本次允许的曲目，要么不改变待播队列；
- 空闲、忙碌、并发改队列、重复消息、部分歌曲不可播放等场景均有确定语义；
- QQ 与 Panel 共用同一服务，展示可不同，但选中的专辑和最终队列结果必须一致；
- 操作延迟、上游错误、成功/跳过数量和批次来源可诊断，且不泄露 Cookie、播放 URL 或用户标识。

### 3.2 非目标

- 首版不支持网易云、B 站等跨平台专辑聚合；
- 不做“相似专辑推荐”、新碟广场、收藏专辑或个人音乐库同步；
- 不自动识别盗版、重制版、豪华版之间的内容等价关系；
- 不在入队时下载整张专辑、预取全部封面或解析全部播放地址；
- 不承诺随机播放模式下保持专辑曲序；
- 不新增一套独立队列、独立 Redis 列表或仅供 Panel 使用的业务 API；
- 不把 QQMusic 上游原始响应直接透传给 QQ 或浏览器。

## 4. 用户与核心场景

| 场景 | 用户意图 | 成功结果 |
| --- | --- | --- |
| 精确专辑 | “播放周杰伦的《叶惠美》” | 选中正确发行版本并按曲序加入 |
| 重名消歧 | 搜索同名专辑或多个版本 | 候选展示歌手、年份、版本标签、曲目数 |
| 试听部分 | 只想听开头或某一段 | 支持前 N 首或 `起始-结束` 范围 |
| 空闲开播 | 当前没有正在播放的歌曲 | 第一首开始播放，其余歌曲进入待播 |
| 忙时排队 | 当前已有播放或待播内容 | 所选曲目作为连续批次追加到队尾 |
| 受限曲目 | 专辑中存在 VIP、下架或地区限制歌曲 | 已知不可播项不入队；未知项播放时失败则自动跳过并记录 |
| 多人同时操作 | 其他用户同时点歌、删歌或拖拽 | 不覆盖他人结果，不产生半张专辑 |
| 重复投递 | QQ 重试同一条消息 | 相同请求只提交一次，并返回原结果摘要 |

## 5. 产品决策

### 5.1 默认限制

建议首版默认值如下，最终应由压测和测试服数据确认：

| 项目 | 默认值 | 理由 |
| --- | ---: | --- |
| 专辑候选数 | 5 | 适配 QQ 按钮和移动端阅读 |
| 曲目预览每页 | 10 | 与现有搜索/排行榜展示密度一致 |
| 会话有效期 | 5 分钟 | 与现有搜歌和榜单会话一致 |
| 单次最多提交 | 30 首 | 防止一人长期占用队列和上游资源 |
| 专辑元数据缓存 | 10 分钟、最多 128 项 | 降低重复详情请求且保持有界 |
| 幂等结果保留 | 10 分钟 | 覆盖 QQ 消息重投窗口 |
| 关键词长度 | 100 字符 | 与现有搜歌限制一致 |

包含超过 30 首的专辑不得静默截断。“整张加入”应返回明确提示并要求使用范围，例如
`专辑加入 1-30`、`专辑加入 31-45`。配置项为 `OOPZ_ALBUM_REQUEST_MAX_TRACKS`，允许值 `1-100`；
更高上限暂不支持。

### 5.2 排序与去重

- 排序键依次为 `disc_number`、`track_number`、上游返回位置；缺失字段不得被当作 `0` 排到最前；
- 多碟专辑按 Disc 1、Disc 2 顺序连续排列，显示编号使用整张专辑的一基连续编号；
- 同一 `song_mid` 在同一专辑响应中重复出现时只保留第一次，并记录上游数据异常；
- 不根据歌名去重：Live、伴奏、重制和不同演唱者可能是合法的不同曲目；
- 已存在于当前或待播队列的歌曲默认仍可再次加入，保持现有点歌语义；首版不引入隐式去重。

### 5.3 队列、公平性与播放模式

- 默认追加到队尾，不提供普通用户“整张插队”；
- 当前无歌曲时，整批提交后触发现有 `play_next` 路径开播第一首；
- 当前有歌曲时，不打断 current；整批曲目在队列中保持连续；
- 每个队列项记录同一 `batch_id` 和专辑来源，供 Panel 展示与诊断，不改变现有一基位置语义；
- 随机模式不重写为顺序模式；提交成功文案显示顺序可能被随机规则打散；
- 单曲循环模式下专辑可以成功入队，但明确提示要切换播放模式后才会自然前进；
- 管理员未来可增加“移动整个专辑批次”能力，但不进入首版。

### 5.4 失败口径

- 元数据阶段已知无版权、仅视频或没有 `song_mid` 的曲目不入队，并在确认页标记；
- 无法判断可播放性的曲目允许入队，轮到播放时才解析地址；
- 播放地址主音质失败时沿用现有回退音质；仍失败则记录 `unplayable`、通知并自动尝试下一首；
- 一张专辑连续 3 首解析失败时暂停自动跳过，提示管理员检查 Cookie/上游，避免故障时快速扫完整个队列；
- 上游专辑详情失败、响应不完整或曲序不可信时不写队列。

## 6. 用户交互设计

### 6.1 命令集

| 命令 | 作用 | 说明 |
| --- | --- | --- |
| `专辑 <关键词>` | 搜索专辑 | 返回最多 5 个候选 |
| `专辑选择 <编号>` | 选择候选并查看曲目 | 建立/更新当前用户的专辑会话 |
| `专辑曲目 [页码]` | 查看已选专辑曲目 | 默认第 1 页，每页 10 首 |
| `专辑点歌 <编号>` | 从当前专辑点一首 | 复用现有单曲播放服务 |
| `专辑加入 全部` | 将整张专辑加入 | 超出单次上限时拒绝并提示范围 |
| `专辑加入 前<N>首` | 加入开头 N 首 | N 不超过单次上限 |
| `专辑加入 <起>-<止>` | 加入闭区间 | 示例：`专辑加入 3-8` |
| `专辑加入 <编号...>` | 跳选多首曲目 | 示例：`专辑加入 1 3 5 7 9`；保持输入顺序并忽略重复编号 |
| `取消专辑` | 清除当前专辑会话 | 不撤销已经入队的歌曲 |

兼容别名只保留必要集合：`选专辑` 等同 `专辑选择`，`整张加入` 等同 `专辑加入 全部`。
不接受裸数字作为选择，避免与现有搜歌会话、排行榜会话冲突。

### 6.2 QQ 流程

```text
用户：@机器人 专辑 叶惠美 周杰伦
机器人：返回 1~5 个专辑候选
        1. 叶惠美 — 周杰伦（2003，11 首）
        2. 叶惠美（现场版）— 周杰伦（……）
        [查看 1] [查看 2] ...

用户：点击“查看 1”或发送 专辑选择 1
机器人：返回专辑信息和第 1 页曲目
        [整张加入] [前10首] [下一页]
        [点第1首] [点第2首] ...

用户：点击“整张加入”
机器人：已加入《叶惠美》：11 首；当前播放 1 首，待播 10 首
        跳过 0 首；队列版本 42
```

按钮必须提交完整命令文本，不依赖浏览器态；Markdown/Keyboard 发送失败时退回同等可操作的纯文本。
所有多步状态按 `area + requester` 隔离，群 A 的候选不能在群 B 使用。

### 6.3 Panel 流程

- 搜索区增加“歌曲 / 专辑”切换，不以自由文本命令作为唯一入口；
- 专辑搜索结果显示封面、名称、歌手、发行日期、版本标签和曲目数；
- 详情抽屉支持分页、单曲勾选、全选当前允许范围，并实时显示“将加入 N 首”；
- 提交时携带当前 `queue_version`。发生 409 时刷新队列，并要求用户再次确认，不自动在新队列上重放批量写；
- 队列项显示专辑名与“同批次”标识；首版只支持逐首删除和现有拖拽；
- 操作结果展示成功加入、已知跳过、当前播放、待播和失败原因，不只显示“成功”。

## 7. 状态机与会话

```text
无会话
  │ 专辑 <关键词>
  ▼
候选会话 ── 专辑选择 <编号> ──► 详情会话
  │ 过期/取消                       │
  └──────────────► 无会话           ├─ 专辑点歌 <编号> ─► 消费成功后清除
                                     ├─ 专辑加入 <范围> ─► 提交成功后清除
                                     ├─ 专辑曲目 <页> ───► 保持并续期
                                     └─ 过期/取消 ───────► 无会话
```

会话必须使用有界的 typed session store，不新增模块级无上限字典。推荐键为
`(area, requester_id, kind="album")`，内容只保存标准化后的专辑候选/详情和过期时间，不保存播放 URL、Cookie
或上游完整响应。新一次 `专辑 <关键词>` 覆盖该用户旧的专辑会话，但不影响其搜歌/榜单会话。

## 8. 领域与接口契约

### 8.1 领域对象

建议新增不依赖 HTTP、Redis 或 QQ SDK 的不可变 DTO：

```python
AlbumSummary(
    provider, album_id, name, artists, release_date,
    edition, track_count, cover_url,
)

AlbumTrack(
    provider, song_id, name, artists, album_id, album_name,
    disc_number, track_number, duration_ms, cover_url,
    availability,
)

AlbumDetail(
    summary, tracks, provider_order_verified,
)

AlbumBatch(
    batch_id, album_id, album_name, requester_id,
    requested_range, tracks,
)
```

`availability` 仅允许 `playable/unplayable/unknown`。`unknown` 不是失败，表示必须在播放时验证。
`album_id/song_id` 作为字符串保存，禁止转换为整数。

### 8.2 Provider Port

```python
class AlbumCatalogPort(Protocol):
    def search_albums(self, keyword: str, limit: int) -> Sequence[AlbumSummary]: ...
    def get_album(self, album_id: str) -> AlbumDetail: ...
```

QQMusic Adapter 负责兼容上游不同包裹结构、字段名和错误形式；应用服务只能看到标准 DTO。
搜索与详情应使用独立缓存键和指标操作名，不复用歌曲搜索缓存条目。

### 8.3 上游能力门槛

固定版本上线前必须在与生产相同的镜像和 Cookie 条件下完成黑盒契约探针：

1. 确认专辑关键词搜索参数能稳定返回 `album_mid/name/artist/release_date`；
2. 确认专辑详情端点能返回完整曲目、稳定顺序、`song_mid` 和分页/总数；
3. 覆盖普通专辑、多碟、同名不同版本、数字专辑、单曲 EP、含不可播歌曲和无 Cookie；
4. 保存脱敏 fixture 并建立解析测试，fixture 不得包含 Cookie 或播放 URL；
5. 若 `2.4.0` 不满足契约，先单独升级固定版本并完成回归，不把依赖升级和产品入口放在同一提交。

上游项目当前文档展示了 `/getAlbumInfo?albummid=...` 一类专辑能力，但本项目固定的精确版本和搜索类型
仍需以上述探针为准。参考：
[QQ Music API 快速开始](https://sansenjian.github.io/qq-music-api/guide/quickstart.html)、
[上游代码架构](https://sansenjian.github.io/qq-music-api/guide/architecture.html)。

## 9. 应用服务与数据流

### 9.1 单一业务路径

```text
QQ command / Panel action
          │
          ▼
AlbumRequestService
  ├── AlbumCatalogPort ──► QQMusic Adapter ──► pinned QQMusic API
  ├── AlbumSessionStore
  ├── QueueService.submit_batch(..., expected_version)
  └── PlaybackService.ensure_started(area)
          │
          ▼
QueuePort (Redis Lua / in-memory lock)
          │
          ▼
PlaybackService ── just-in-time URL resolution ──► voice runtime
```

QQ renderer 和 Panel route 只能负责输入/输出适配，不得自行遍历曲目、解析 URL 或写 Redis。
旧 `MusicHandler` 只保留必要的语音播放兼容能力。

### 9.2 原子批量入队

`QueueService` 新增 `submit_batch(items, batch_id, expected_version=None)`：

- 先在应用层完整验证数量、范围、必填标识和序号，再调用 QueuePort；
- Redis 使用一次 Lua 操作检查版本、写入整批项目、推进一次 `queue_version`；
- 内存队列在同一把锁内完成等价操作；
- 任一序列化、容量或版本校验失败时不得写入任何曲目；
- `batch_id + request_id` 在幂等窗口内重复时返回首次结果，不再次入队；
- 成功响应采用服务端的新版本和完整摘要，Panel 不把本地乐观数组当作事实源。

批量提交不应同时持有网络请求和队列锁。所有专辑详情读取、标准化和规则校验必须在进入原子写之前完成。

### 9.3 播放地址按需解析

新增队列项可以只保存稳定的 provider/song ID 与展示元数据，`url` 允许为空。轮到播放时：

1. PlaybackService 用 `provider + song_id` 获取当前播放地址；
2. 尝试主音质与现有回退音质，校验空地址和明显错误响应；
3. 仅为 current 和下一首执行现有预加载，不预取整张专辑；
4. 地址解析失败时记录歌曲、专辑批次和结构化错误，不记录 URL；
5. 兼容旧队列中已经存在 `url` 的项目，迁移期先使用可用旧 URL，失效后再按 ID 解析。

该改动应先作为独立基础提交交付，并验证普通单曲、榜单和旧 Redis 数据不回归。

## 10. Bridge 与响应契约

建议新增以下 `reply_type`：

| reply_type | 关键字段 | 用途 |
| --- | --- | --- |
| `album_search_results` | `query/albums/expires_at` | 专辑候选 |
| `album_detail` | `album/tracks/page/page_count/limits` | 详情与确认 |
| `album_song_selected` | `album/song/message` | 专辑内单曲点歌 |
| `album_batch_queued` | `batch_id/album/added_count/skipped_count/current_count/pending_count/queue_version/warnings` | 批量提交结果 |

标准失败码至少包括：

- `album_not_found`
- `album_session_expired`
- `album_selection_out_of_range`
- `album_track_range_invalid`
- `album_track_limit_exceeded`
- `album_metadata_unavailable`
- `album_order_unverified`
- `queue_conflict`
- `queue_capacity_exceeded`
- `duplicate_request`

用户文案可以本地化，但 QQ 与 Panel 的 `ok/code/counts/album_id/batch_id/queue_version` 语义必须一致。

## 11. 并发、容量与安全

### 11.1 并发与一致性

- QQ 重复消息继续使用消息 ID 去重，应用服务再以 `request_id` 做第二层幂等；
- Panel 使用 `expected_version`；冲突时返回 HTTP 409 和最新队列，不自动重试；
- QQ 文本命令没有长生命周期快照，可在提交时读取最新版本并原子追加；
- 多 area 队列、会话、版本和批次必须完全隔离；
- 队列最大容量检查与批量写入必须在同一个原子操作中完成；
- 播放器同时出队不会导致半批加入或重复 current。

### 11.2 安全与隐私

- 所有关键词先裁剪长度和控制字符，再进入日志或上游查询；
- 不接受用户提供的任意 URL 作为专辑源，首版只接受关键词和标准化 album ID；
- album/song ID 在 Adapter 中按允许字符和长度校验，避免路径拼接和日志注入；
- 日志和状态只保存脱敏 requester hash、album ID、数量、耗时和错误类别；
- Cookie、refresh key、播放 URL、QQ OpenID 和上游完整 payload 不进入会话、SSE、Panel 状态或诊断包；
- QQ 群允许列表、Panel Basic Auth 和 Bridge Token 沿用现有边界；
- 外部请求设置连接/读取超时、响应体上限和有限重试，不能在队列锁内重试。

### 11.3 配置建议

| 环境变量 | 默认值 | 作用 |
| --- | --- | --- |
| `OOPZ_ALBUM_REQUEST_ENABLED` | `false` | 灰度总开关 |
| `OOPZ_ALBUM_REQUEST_MAX_TRACKS` | `30` | 单次批量上限，限制为 1-100 |
| `OOPZ_ALBUM_REQUEST_SESSION_TTL_SECONDS` | `300` | 候选/详情会话有效期 |
| `OOPZ_ALBUM_CACHE_TTL_SECONDS` | `600` | 元数据缓存有效期 |
| `OOPZ_ALBUM_CACHE_MAX_ENTRIES` | `128` | 搜索与详情缓存总上限 |

这些变量只有在功能实现时才加入 `.env.example`、配置文档和升级说明。功能关闭时不得发起专辑接口请求，
也不得改变当前命令解析行为。

## 12. 可观测性

新增指标必须复用现有有界指标和 OperationsRegistry：

- `album_search`：次数、成功率、last/p50/p95、缓存命中与并发合并；
- `album_detail`：次数、曲目数分布、响应解析失败、曲序不可信；
- `album_submit`：请求曲目数、实际加入数、已知跳过数、冲突和容量拒绝；
- `album_playback`：按需解析成功率、主/回退音质结果、不可播放和连续失败熔断；
- `album_duplicate_request`：被幂等层拦截的重复提交；
- 最近操作记录显示专辑名的截断/脱敏展示、批次 ID、数量和结果，不显示原始用户标识。

健康检查只报告功能是否启用、最近一次探针结果和错误分类；QQMusic 临时不可用时 readiness 仍沿用现有降级策略，
不能因为可选专辑能力阻止 Bot 启动。

## 13. 分阶段实施

| 阶段 | 任务 | 主要产物 | 发布条件 |
| --- | --- | --- | --- |
| A：上游契约与领域模型 | 对固定镜像做专辑搜索/详情探针；建立 DTO、fixtures、AlbumCatalogPort | 契约报告、解析器、单元测试 | 目标专辑样本均能得到稳定 ID 和曲序 |
| B：队列基础能力 | `submit_batch`、容量检查、幂等批次、JIT 播放地址解析 | QueuePort/PlaybackService 改造与兼容测试 | 普通点歌/榜单/旧队列无回归，批量写原子 |
| C：QQ MVP | 命令、album session、Bridge 契约、Markdown/Keyboard 和帮助 | 可灰度的 QQ 专辑点歌 | 开关关闭零行为变化；纯文本降级可操作 |
| D：Panel 与运维 | 搜索类型、详情抽屉、版本冲突处理、指标和文档 | QQ/Panel 能力对齐 | SSE、重连、409、移动端和权限验收通过 |

建议每阶段单独提交并更新 `CHANGELOG.md`。如果 A 阶段要求升级 QQMusic 包，应将依赖升级作为额外独立提交，
先在生产关闭 `OOPZ_ALBUM_REQUEST_ENABLED` 的状态下观察现有搜歌、排行榜和播放成功率。

## 14. 测试计划

### 14.1 自动测试

| 层级 | 必测内容 |
| --- | --- |
| Provider 契约 | 多种包裹结构、字段缺失、多碟顺序、重复 mid、分页、超时、401/403、空响应、超大响应 |
| 会话 | requester/area 隔离、覆盖、续期、过期、取消、与搜歌/榜单会话共存 |
| 命令解析 | 中文空格、全角字符、别名、非法编号、反向范围、超限、裸数字不抢占其他会话 |
| QueueService | 批量全成或全败、容量边界、一次版本递增、409、Redis/内存等价、并发出队 |
| 幂等 | 相同 request ID 重放、超时后重试、不同用户相同专辑、窗口过期后允许新提交 |
| PlaybackService | 空 URL 队列项、主/回退音质、连续失败熔断、旧 URL 兼容、只预加载下一首 |
| QQ | Markdown/Keyboard、按钮命令、主动消息失败后的纯文本回退、长专辑分页 |
| Panel | 专辑搜索、范围选择、提交计数、409 刷新、SSE 更新、键盘和触摸操作 |
| 安全 | Secret/URL/OpenID 脱敏、关键词限制、响应体上限、缓存和会话容量 |

### 14.2 人工验收样本

至少准备以下真实专辑，每次发布记录 album ID，避免只凭名称复测到另一个版本：

- 普通录音室专辑（10-15 首）；
- 同名不同歌手专辑；
- 原版与豪华/重制版并存；
- 双碟或多碟专辑；
- 超过 30 首的合集；
- 含 VIP/下架/地区限制曲目；
- EP/单曲专辑；
- 中文、英文、日文名称和特殊符号名称。

人工流程覆盖：空闲开播、忙时追加、随机/单曲循环提示、入队后删歌与拖拽、两人同时提交、
QQ 重复消息、Cookie 过期、QQMusic 重启、Redis 短暂不可用和 Bot 重启恢复。

### 14.3 性能门槛

- 缓存未命中的专辑搜索 p95 不高于同环境普通搜歌 p95 的 1.5 倍；
- 缓存命中的搜索/详情不访问上游，服务端处理 p95 小于 100 ms；
- 30 首批量入队只发生一次 Redis 写事务和一次 `queue_version` 递增；
- 提交阶段不请求 30 个播放地址，端到端响应不随曲目数线性叠加网络延迟；
- 缓存、会话、幂等表和操作历史达到上限后内存不继续增长；
- Panel SSE 事件大小保持有界，不在每次状态变化中发送完整专辑详情。

## 15. 上线、灰度与回滚

### 15.1 灰度步骤

1. 在测试服运行固定版本 API 契约探针并保存脱敏结果；
2. 关闭功能开关部署 B 阶段基础改动，验证普通点歌、搜歌、榜单、切歌和旧 Redis 队列；
3. 仅对白名单测试群开启 QQ MVP，观察 24 小时搜索、提交、不可播放和重复请求；
4. 开放 Panel，验证版本冲突、SSE 和移动端；
5. 指标稳定后默认开启，并更新 README 命令表、配置文档和发布检查清单。

### 15.2 停用与回滚

- 紧急停用只需设置 `OOPZ_ALBUM_REQUEST_ENABLED=false` 并重启 Bot；已入队歌曲仍按普通队列项播放；
- 回滚应用代码前不需要清空 Redis，新增队列字段必须允许旧版本忽略；
- 如果旧版本不能处理 `url` 为空的队列项，B 阶段发布前必须提供兼容读取或显式的回滚转换命令，
  并在 Upgrade notes 写明备份和操作步骤；
- 不自动删除已经提交的专辑批次，不把代码回滚与数据恢复绑定；
- QQMusic 依赖若曾升级，保留旧镜像标签，可独立回滚并运行现有四个核心端点探针。

## 16. 验收标准

功能只有在以下条件全部满足时才算完成：

- 用户能从 QQ 和 Panel 搜到并区分同名/多版本专辑；
- 选择前能看到专辑信息和曲目范围，任何入队都需要显式确认；
- 顺序模式下，多碟专辑和范围点歌的最终播放顺序正确；
- 30 首批量提交没有部分写入、重复写入或 N 次队列版本递增；
- 空闲时第一首启动，忙碌时不打断 current，随机/单曲循环场景提示准确；
- 不可播放曲目不会让整条播放链永久卡住，连续上游故障也不会快速耗尽队列；
- QQ 与 Panel 对同一请求返回一致的 album ID、计数、批次和队列版本；
- 功能关闭、上游异常、Redis 降级和旧队列数据下，现有单曲/榜单能力无回归；
- 日志、状态、SSE、诊断包和测试 fixture 不包含 Cookie、播放 URL 或原始用户标识；
- README、配置说明、架构文档、发布检查清单和 `CHANGELOG.md` 与实际行为一致。

## 17. 立项前待确认项

以下问题应在阶段 A 用证据关闭，而不是在实现中临时猜测：

1. 固定 `2.4.0` 镜像是否同时支持专辑类型搜索和完整专辑详情，实际路由、参数和响应是什么；
2. 多碟曲目的 disc/track 字段是否稳定，若缺失，上游顺序是否足以作为可信回退；
3. 专辑详情是否分页、最大返回数是多少，数字专辑和 VIP 曲目的可播放标记是否可信；
4. 现有旧播放核心对 `url` 为空的 Redis 队列项有哪些读取路径，回滚兼容需要做到哪一层；
5. 生产队列容量与典型长度是多少，30 首默认上限是否需要下调；
6. QQ Markdown/Keyboard 当前模板限制能否稳定展示 5 个专辑候选和 10 个曲目按钮。

这些问题不阻止领域与测试设计，但任何一个关键契约未确认，都应保持功能开关默认关闭。
