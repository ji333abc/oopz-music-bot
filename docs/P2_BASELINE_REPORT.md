## 1. 基线结论

- Panel 当前每 10 秒请求一次完整 `/api/state`。单浏览器空闲运行时理论上产生 360 次/小时、
  8,640 次/天的完整状态请求；Bot 快照生成次数与请求次数同阶增长。
- 播放进度由浏览器每秒插值，完整快照轮询主要用于队列、播放语义状态、频道、健康、事件和 JM 状态校准。
- P2 开始前没有端点延迟窗口、命令耗时、最近播放、结构化失败或状态 revision。
- 原状态文件 schema 为 `version=1`，事件持久化上限 100、JM 任务持久化上限 50，Panel 各展示最近 30 条。
- Redis 队列批量删除已经使用原子操作，但 Panel 写请求没有队列版本，旧编号可能在并发变化后指向另一首歌。
- 默认 Bot 镜像仍安装 JM 依赖；本机没有 Docker，镜像体积、冷构建时间和容器资源不能在本轮可靠采集。

## 3. P2-01 容量契约

| 数据 | 默认硬上限 | 超限行为 |
| --- | ---: | --- |
| 单个外部端点延迟样本 | 200 | 丢弃最旧样本 |
| 外部指标序列 | 64 | LRU 淘汰最旧序列并计数 |
| 最近播放 | 50 | 丢弃最旧记录 |
| 最近命令 | 200 | 丢弃最旧记录 |
| 最近结构化失败 | 100 | 丢弃最旧记录 |
| Panel 事件 | 100 | 保持既有上限 |
| JM 任务 | 50 | 保持既有上限 |
| Panel 单类历史展示 | 30 | 快照只返回最近记录 |
| `panel-state.json` | 512 KiB | 拒绝写入超出硬上限的状态 |

延迟百分位使用 nearest-rank：空窗口返回 `null`；单样本的 p50/p95 均为该样本；混合成功/失败样本
共同参与延迟分布，成功数与失败数分别报告。耗时使用单调时钟，UTC 时间只用于展示和持久化。

## 4. 已建立的自动化证据

- 指标模块没有 FastAPI、Redis、requests、Panel 或其他网络/UI 框架依赖；
- 有界窗口会淘汰最旧样本，指标 registry 同时限制样本数和序列数；
- Fake Clock 可验证单调耗时，无测试 `sleep`；
- 旧 `version=1` 状态文件自动迁移到当前 schema，保留组件、事件和 JM 数据；
- 旧文件和新历史记录在持久化前统一脱敏并按容量裁剪；
- P2-01 针对性测试通过；Python 全量 203 项通过、2 项按既有条件跳过；全仓 Ruff、Panel lint 和
  Python compileall 通过。
